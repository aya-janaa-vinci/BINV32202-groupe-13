Gesta · Architecture applicative

Visualiser une offre, de l'écran à la base de données

Le parcours de lecture d'une offre suit une chaîne contrôlée : le frontend demande les données, le backend identifie l'utilisateur, applique les règles de visibilité, interroge SQLite, puis renvoie un DTO adapté à l'affichage.

Point d'entrée GET /api/offers
Appel déclenché par OffersPage après authentification.

Le parcours en cinq étapes

1

La page se monte

App.tsx transmet l'utilisateur, le jeton et la fonction de déconnexion à OffersPage.

2

Le hook charge

useOffers lance getOffers dans un effet et gère chargement, erreur et annulation.

3

L'API reçoit

Le proxy Vite retire /api. Express authentifie puis autorise la requête sur /offers.

4

Le backend filtre

Le service détermine le filtre selon le profil et le repository exécute la requête SQL avec ses jointures.

5

L'écran se met à jour

Le JSON est validé, stocké dans l'état React, puis rendu par OfferTable.

1 · Du frontend vers le backend

Déclenchement et appel HTTP

Quand la route /offres est affichée, OffersPage.tsx appelle useOffers(token, onUnauthorized). Le hook crée un AbortController puis demande les offres via frontend/src/services/offers.service.ts.

  • URL appelée : /api/offers
  • En-tête : Authorization: <token>
  • Réponse attendue : un tableau d'offres

Proxy et validation

Vite redirige /api/offers vers l'API backend, en supprimant le préfixe /api. Le service appelle ensuite readJson, qui vérifie le statut HTTP et le type de chaque champ avec isOfferList.

  • 401 : déconnexion et retour à la connexion
  • Autre erreur : affichage de ErrorState
  • Réponse valide : stockage dans offers

2 · Contrôle côté backend

Authentification puis autorisation

La route est montée dans app.ts derrière le middleware authenticate. Le token identifie l'utilisateur ; le backend relit ses informations en base. Ensuite authorize(canListOffers) vérifie qu'il possède le droit de consulter les offres.

Contrôleur et service

offers.controller.ts récupère l'utilisateur courant et appelle offersService.listOffers. Le service choisit le filtre, appelle le repository, transforme les données avec toOffer, puis le contrôleur transforme chaque offre en DTO avec toOfferDto.

3 · Les règles de visibilité

Administrateur

Aucun filtre de statut ni de déposant : toutes les offres sont retournées.

Étudiant

Le service ajoute status = PUBLISHED : seules les offres publiées sont visibles.

Contact déposant

Le service ajoute depositorContactId = user.id : seules ses offres sont visibles.

4 · Lecture SQLite et transformation

Requête du repository

offers.repository.ts joint les tables companies, academic_years et periods. Les résultats sont triés par année académique décroissante puis par date de création décroissante.

  • Filtre de statut optionnel
  • Filtre de déposant optionnel
  • Retour d'un objet DBO contenant les noms SQL

DBO, modèle métier, DTO

Le DBO utilise des champs comme company_short_name. Le mapper le convertit en objet métier, puis le DTO public conserve uniquement les champs nécessaires à la liste. Cette séparation évite d'exposer la description, les identifiants internes ou les dates techniques.

Branches d'erreur

401 · Session invalide

Le hook appelle onUnauthorized, le token est supprimé et l'application revient à l'écran de connexion.

403 · Accès refusé

Un contact qui n'a pas le rôle déposant ne peut pas consulter les offres ; le backend refuse la requête avant la lecture SQL.
